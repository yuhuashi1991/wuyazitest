## 3. 核心概念（4 个）

每个概念都按六问交代。不要背定义，抓住「查询订单打到一台已经在跑的机器上」这一件事。

### 3.1 JDK vs JVM

- **它解决什么问题：** 你需要一套工具把 `.java` 编成能跑的东西（JDK，Java Development Kit），还需要一个运行时真正去执行（JVM，Java Virtual Machine）。没有 JDK 通常编不了；没有 JVM 编出来也跑不了。
- **它在项目中的位置：** 整张地图的最底下。订单管理 API 无论几层，最终都是「某台机器上的某个 JVM 进程」。
- **前端工程师需要理解到什么程度：** 能类比「装了 Node.js 才能跑 JS；但 `tsc` 编译和 `node` 执行不是同一件事」。JDK 里通常带着编译器 `javac` 和用来启动 JVM 的 `java` 命令。不要求会装发行版差异，不要求背版本矩阵。
- **使用 AI 时应该怎样描述需求：** 写清操作系统、是否已安装 JDK、目标是「编译」还是「运行」、成功时你期望看到什么输出。不要只说「帮我配一下 Java」。
- **AI 最容易在这里犯什么错误：** 把 JDK 和 JRE/JVM 混为一谈；给你一串改业务代码的步骤；假设你已经装好却不验证 `javac -version` / `java -version`。
- **我应该如何验证：** 终端里两个命令都有输出，且能编译、能运行今天的小程序。只装了运行时、没有 `javac`，下一步会在「编译」这一步失败。

### 3.2 源码 → 字节码 → 运行

- **它解决什么问题：** 浏览器不能直接执行 `.java`。要先编译成 `.class`（里面是字节码），再交给 JVM 翻译/执行。这和前端「`.ts` → 编译产物 → `node` 跑」同一类分工，产物格式不同。
- **它在项目中的位置：** 仍在底座。真实项目里 Maven 会替你调用编译；今天用手敲 `javac`，是为了看清产物，而不是让你以后天天手编。
- **前端工程师需要理解到什么程度：** 知道编译产物是 `.class`（不是再把 `.java` 当脚本解释）；知道运行时指定的是**类名**，不是文件内容本身。classpath（类路径）的直觉：JVM 去哪些目录找 `.class`。单文件时，当前目录往往就是 classpath。
- **使用 AI 时应该怎样描述需求：** 「先 `javac` 再 `java`；告诉我 `.class` 会出现在哪；不要换成别的构建工具。」
- **AI 最容易在这里犯什么错误：** 让你 `java OrderServiceApp.java` 混用源文件当入口（新版本有时能跑，但会掩盖「先有字节码」这件事）；或甩出 Maven/Gradle 却不说明今天用不到。
- **我应该如何验证：** 编译后同目录出现 `OrderServiceApp.class`；用 `java OrderServiceApp` 能看到启动日志。删掉 `.class` 再运行，应该失败——失败也是验证。

JIT（Just-In-Time compilation，运行中再把热点字节码编成本地机器码）和字节码指令细节：理解用途即可。JVM 调优、类加载器实现：暂时跳过。

### 3.3 入口类与 `main`

- **它解决什么问题：** JVM 启动时要知道「从哪一行开始跑」。约定是某个类里的 `public static void main(String[] args)`。Spring Boot 项目里你看到的启动类，本质上也是带 `main` 的入口；框架在 `main` 里把 Web 容器拉起来。
- **它在项目中的位置：** 进程的点火开关。查询订单的 Controller 不是入口；入口先把进程点着，请求来了才进到那一层。
- **前端工程师需要理解到什么程度：** 能在文件里指认 `main`；知道 `String[] args` 是命令行参数（类似 `process.argv`）。不要求背修饰符含义，不单开语法课。
- **使用 AI 时应该怎样描述需求：** 「入口类是哪个、`main` 在哪一行；运行命令用类名还是 jar；成功日志是哪一句。」
- **AI 最容易在这里犯什么错误：** 指错启动类；编造一个项目里不存在的 `main`；把测试类当成启动入口。
- **我应该如何验证：** 命令里写的名字，必须和 `public class 名字` 对得上；启动后第一行日志能对上你读过的 `println`。

### 3.4 后端是长期运行的进程，不是一次性脚本

- **它解决什么问题：** 前端静态页可以「打开就算一次」；订单服务必须先占着进程（以后还会占端口），查询请求才能打进来。进程挂了，接口再对也没人接。
- **它在项目中的位置：** 地图上「Spring Boot 进程」那一格的运行形态。今天的小程序用循环模拟「还活着」；真实服务会一直监听 HTTP。
- **前端工程师需要理解到什么程度：** 类比 `node server.js` 一直挂着，而不是 `node build.js` 跑完就退出。不要求会写线程或端口监听。
- **使用 AI 时应该怎样描述需求：** 「这是长期进程；成功判据是进程还在、日志出现已启动，而不是程序立刻结束码为 0 就算完。」（今天的示例用交互循环保活；以后 Spring Boot 是占用端口。）
- **AI 最容易在这里犯什么错误：** 写一个查完订单就 `System.exit` 的脚本，还说「服务启动成功」；或把「编译成功」当成「服务在跑」。
- **我应该如何验证：** 启动后终端还在等你输入；另开思路：若进程已退出，就没有任何「查询订单」可以被处理。

## 4. 一个业务场景

想象一台叫「订单服务」的机器。产品要的是：前端（或以后的 HTTP 客户端）查询 `ORD-1001`。

关键约束：**请求到达之前，Java 进程必须已经在跑。**

时间顺序是：

1. 人（或部署脚本）在机器上启动订单服务 → 得到一个 JVM 进程。
2. 进程活着，内部才谈得上以后的 Controller → Service → 查库。
3. 这时「查询订单」才有接收者。
4. 若进程没启动、启动失败、或已经退出：不是业务规则错了，是底座没人值班。

今天用最小 `main` 模拟第 1 步和第 3 步的「查询」：先启动进程，再在进程里查一笔内存里的订单。没有 Tomcat、没有端口、没有表——那些在地图上，但不是今天的关卡。

## 5. 最小可运行代码

把下面保存为 `OrderServiceApp.java`（类名必须和文件名一致）。它不是订单管理 API 的业务实现，只是让你看见：**编译 → 进程 → 查询订单**。

```java
import java.util.Scanner;

public class OrderServiceApp {

    public static void main(String[] args) {
        System.out.println("[OrderService] JVM 进程已启动，正在等待查询订单");
        System.out.println("[OrderService] 输入订单号后回车；输入 exit 结束进程");

        Scanner scanner = new Scanner(System.in);
        while (true) {
            System.out.print("query> ");
            String orderId = scanner.nextLine().trim();
            if (orderId.equals("exit")) {
                System.out.println("[OrderService] 进程即将退出");
                break;
            }
            if (orderId.equals("ORD-1001")) {
                System.out.println("{\"orderId\":\"ORD-1001\",\"status\":\"PAID\"}");
            } else {
                System.out.println("订单不存在: " + orderId);
            }
        }
    }
}
```

本机（或沙箱）在该文件所在目录执行：

```bash
javac OrderServiceApp.java
java OrderServiceApp
```

成功时你应看到启动两行日志、提示符 `query>`，进程**不立刻结束**。输入 `ORD-1001` 应得到 JSON 形态的一行；输入 `exit` 后进程才退出。同目录应出现 `OrderServiceApp.class`——那才是 JVM 加载的东西。

语法只在现场补：`main` 是入口；`while (true)` 表示进程还活着；`Scanner` 从标准输入读一行，用来模拟「查询到达」。不需要先复习循环教材。

## 参考答案

先自己写完第 6 节预测和第 9 节理解题再往下看。答错时看「缺的是哪一块认知」，不要只记标准句。

### 代码阅读预测

1. **产物：** 同目录多出 `OrderServiceApp.class`。它是编译得到的字节码，给 JVM 加载；`.java` 仍是给人看的源码。没有这份 `.class`（又没有别的打包方式）时，按今天的命令是跑不起来的。
2. **谁在跑：** 真正执行的是 **JVM**，加载的是 **`.class`**。JDK 提供了 `javac`（编译）和启动 JVM 的 `java` 命令本身。命令里的 `OrderServiceApp` 是**类名**，不是「把源文件当脚本」；默认从当前目录（classpath）找 `OrderServiceApp.class`。
3. **没启动就查询：** 没有进程在值班，查询没有接收者——不是返回「订单不存在」，而是连处理查询的那一方都不存在。打开本地 HTML 是浏览器用一次性加载文件；订单服务是长期进程，请求是打到活着的进程上。
4. **删掉 `main`：** `javac` 往往仍能编过（类还在）；`java OrderServiceApp` 会在**运行期**失败，提示找不到 `main` 方法。用这句报错确认：失败点是「入口约定」，不是「文件不存在」。
5. **表格：** 必须讲清 JDK、JVM、`javac`/编译、运行、classpath 直觉。JIT、字节码细节 → 理解用途。类加载器实现、JVM 调优 → 暂时跳过。

### 理解题

1. **缺编译器这一侧。** JVM 只能跑已经编出来的字节码。证明：`javac -version` 若命令不存在，说明只有运行时或 PATH 不对，还不能按今天的方式编订单服务。`java -version` 有输出不等于能编译。
2. **打到已经存在的 JVM 进程。** 正式 API 要反复接请求、保持内存/连接/以后的端口；每次查询都冷启动一个 JVM 又退出，延迟、状态、资源都不可用。今天循环里的 `query>` 就是在模拟「进程还活着才能查」。
3. **三件事：** 当前工作目录是不是 `.class` 所在目录；命令里的类名是否正好是 `OrderServiceApp`（大小写敏感）；有没有误加包名或把 classpath 指到别处。先 `ls`（或 dir）看 `.class` 在不在，再运行。
4. **Nginx、Redis、SpringCloud 在本期都是「理解用途」（知道解决什么问题、何时会碰到），不是本周必须实现；其中更重的操作与原理深挖（如 ES/ZK 等）还在「暂时跳过」。** 第一周接 Redis 会把第一期范围撑破：今天只要求底座能讲清、能验证启动。
5. **两类废话：** 一是擅自改业务、上 Spring/Maven/Docker；二是只说「装个 JDK 再运行」却没有可复制命令和可观察的成功判据。今天指令里的四个防废话要素：**禁止改业务 / 可复制命令 / 成功判据 / 失败时只诊断不改源码**（需求、上下文、报错、验收，四件套的最小版）。
